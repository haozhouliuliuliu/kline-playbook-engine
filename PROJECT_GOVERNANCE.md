### Dynamic-state rule

The following volatile fields belong only in `CURRENT_STATE.md`, except where an exact machine/Owner execution authority necessarily contains its own bound executable values:

- `CURRENT_WORK_PACKAGE`;
- `WORK_PACKAGE_PHASE`;
- `CURRENT_ACTIVITY`;
- `NEXT_TASK`;
- current hold/lock state;
- current provider-execution readiness/hold state;
- current paid-slot pointer.

Stable files may point to `CURRENT_STATE.md`; they must not copy those values.

### Exact execution rule

Exact spend ceilings, call ceilings, retries, exact model/provider request identity and executable slot state live in the exact Owner execution authority plus its machine-readable authority.

`CURRENT_STATE.md` may state whether that exact slot is currently active, held, consumed or locked and must link to the exact authority. Other stable files must not duplicate that live state.

## 4. Secrets and credential location

Secret **values** never belong in Git, project docs, logs, screenshots generated by project tooling, or chat memory.

A stable credential **location contract** may be recorded in `TOOL_REGISTRY.md`, including environment-variable name and expected local scope.

Runtime may check only non-secret availability such as `SET / UNSET` unless an exact provider client needs to consume the value internally.

Never print, echo, serialize, persist or commit the secret value.

## 5. Fresh-conversation continuity

A new project brain must:

1. refresh current GitHub `main`;
2. start at `00_READ_FIRST.md`;
3. read the stable authority owners listed there;
4. read `CURRENT_STATE.md` as the sole current dynamic-state owner;
5. follow the task-specific authority pointers from `CURRENT_STATE.md`;
6. never reconstruct current state from old chat, stale branches or deleted snapshots.

A new conversation should not need historical archaeology for normal takeover.

## 6. Shared authority / integration lane

Exactly one integration lane may modify `main` or shared authority at a time.

Parallel workers:

- use separate branches/worktrees;
- do not independently edit shared authority unless assigned to the integration lane;
- do not push competing current-state changes from stale parents;
- must refresh `main` before integration.

Merge conflicts and semantic conflicts in shared authority are project defects, not harmless documentation noise.

## 7. Anti-drift verification

Repository verification must mechanically check, at minimum:

- required active authority files exist;
- `00_READ_FIRST.md` contains the stable takeover owners;
- volatile dynamic-state keys do not appear in stable-owner files;
- active-core file references resolve to existing repository paths;
- `CURRENT_STATE.md` contains one coherent current state rather than contradictory duplicate states.

The repository checker is a guard, not a replacement for Owner authority or human/project-brain judgment.

## 8. Deletion / migration rule

Do not delete an active authority merely because the active context is large.

Before deleting or folding an authority:

1. identify the concern it owns;
2. identify the successor owner;
3. migrate still-binding semantics;
4. record the migration when material;
5. update takeover navigation;
6. verify no live responsibility was orphaned.

Git history preserves obsolete history; it does not by itself replace a currently binding authority owner.

## 9. Current-state isolation

`PROJECT_DIRECTION.md`, `ARCHITECTURE_BASELINE.md`, `TOOL_REGISTRY.md`, `README.md`, `KNOWN_LIMITATIONS_AND_TECH_DEBT.md`, `AGENTS.md`, `PROJECT_BRAIN_RUNTIME_BRIEF.md` and `00_READ_FIRST.md` must remain free of current work-package/phase/next-task/spend-slot duplication.

not a synchronized rewrite of every root document.
